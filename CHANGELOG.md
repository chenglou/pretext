# Changelog

## Unreleased

### Added

- Rich inline takes boxes, `{ width }` (`RichInlineBox`), for an image, a custom emoji, a formula or a badge inside a line, in place of a character with `break: 'never'` and an `extraWidth` that made up the rest of the object's width. A line can break before and after a box, as at an `<img>`, whatever text touches it, and its fragment has the box's width and no text. Heights stay yours: give each box `vertical-align: top`, and each line is as tall as the paragraph's line height or its tallest box, whichever is taller. `prepareRichInline()` now takes `Array<RichInlineItem | RichInlineBox>`, so code typed from its parameter checks an item's `text` before reading its text or font, and `RichInlineItem` has `width?: never`, so an app whose own run type carries a `width` beside its `text` no longer type-checks at `prepareRichInline()`: pass such runs without that field, or name it otherwise; at run time such an item still lays out as text (#387).
- `prepareRichInline()` takes an options argument, `{ whiteSpace: 'pre-wrap' }`, for CSS `white-space: pre-wrap` on the paragraph, as `prepare()` does: every item but an atomic one keeps its spaces, tabs and newlines, spaces at a line's end hang past it across a change of style, tab stops count from the line's start, and a newline ends its line, so an editor's paragraph split into styled runs takes the lines the browser gives it. White space after an atomic item wider than the line stays on that item's line, whatever items it spans; in Firefox, such white space that runs into a tab moves to the next line with the tab. A tab counts its stops in its own item's font, as Safari does; Chrome and Firefox count them in the paragraph's font, so a tab inside a span in another font, such as a code span, can land a whole stop from theirs. `paragraphs.map(prepareRichInline)` no longer type-checks, since `map()` hands its index where the options go: write `items => prepareRichInline(items)` (#381, #386, #395, #419, #460).
- `prepareRichInline()`'s options argument also takes `{ wordBreak: 'keep-all' }`, for CSS `word-break: keep-all` on the paragraph, as `prepare()` does, so Korean, Chinese and Japanese messages with mentions, bold runs or code spans break where the browser breaks them under keep-all (#379).
- Rich-inline fragments now have `gapItemIndex`, the index of the item whose collapsed space `gapBefore` measures, or -1 when no space precedes the fragment on its line. A painter can draw that space inside the element of the item whose font measured it, and can tell a space that takes no room apart from no space (#310).
- Materialized rich-inline fragments now have `sourceStart` and `sourceEnd`, where the fragment's text sits in its item's `text`, as UTF-16 offsets: of the items `Ship` and ` it now`, the fragment `it now` is 1 to 7. Read them where code written for 0.0.9 read the fragment's `start` and `end` as cursors into the item's own text, which they no longer are (under Changed). TypeScript that builds a fragment by hand, as a test does, now has to give it these two and `gapItemIndex`; a fragment range built by hand needs `gapItemIndex` (#460).
- `walkLineRanges()`, `measureLineStats()`, `measureNaturalWidth()` and `layoutNextLineRange()` now also take a `prepare()` handle, so an app that only needs line counts, widths or cursors, such as a chat bubble shrunk to its widest line, no longer has to keep every segment's string in memory with `prepareWithSegments()`. `layoutWithLines()`, `layoutNextLine()` and `materializeLineRange()`, which return text, still need `prepareWithSegments()` (#449).

### Changed

- Bundles that import Pretext are larger than with 0.0.9: the main entry is about 41 KB gzipped (97 KB minified), up from 16 KB (48 KB), and `@chenglou/pretext/rich-inline` about 45 KB (108 KB), up from 16 KB (49 KB). About 23 KB gzipped of each is each browser's line-break and grapheme data with the code that reads it, which replace Pretext's own break rules and the Unicode bidi-class table that 0.0.9 bundled for `segLevels`. The npm package is 60 files and about 1,030 KB unpacked, where 0.0.9 was 69 files and 887 KB, 534 KB of it the demos, which have left the package (#258, #311, #340, #342, #344, #392, #394, #403, #460).
- Speed against 0.0.9, timed in Chrome 154, Firefox 156 and Safari 27 on an M5 Max MacBook Pro, on chat-like messages (#338, #340, #344, #351, #365, #375, #383, #400, #407, #435, #445, #453, #460):
  - Faster: `layout()` at a new width is three to six times as fast. `measureLineStats()` and `walkLineRanges()` are 1.8 to 4.7 times as fast, `layoutWithLines()` 1.3 to 1.7 times and `layoutNextLineRange()` 1.1 to 2.2 times. `prepare()` of text it has measured before, as when a list prepares its messages again, is 1.1 to 12 times as fast: two to three times for English text, 6 to 12 times for Chinese and Japanese, least for Thai. Text it hasn't measured before is about 1.5 to 2.4 times as fast for English, Chinese and Japanese, 1.2 to 1.6 times for messages that mix scripts, and from level to 1.8 times for Arabic and Thai. Rich inline, timed on the Markdown chat demo's paragraphs (English, most of them one item), prepares and measures new ones about 1.3 to 1.5 times as fast and ones it has measured before two to four times as fast. `measureRichInlineStats()` is two to three times as fast there, and `walkRichInlineLineRanges()` and `layoutNextRichInlineLineRange()` 1.1 to 1.9 times, least on paragraphs of several styled items. Worst-case text, such as letter-spaced CJK, soft hyphens among combining marks, long unbroken runs and `pre-wrap` text, is faster too, in `prepare()` and in `layout()`.
  - Slower: loading the library, timed as a bundle of both entry points, takes about 0.5 ms more on each page in Chrome, 0.7 ms in Safari and 1.2 ms in Firefox, and the first text a page prepares, its first few hundred to a thousand characters, takes about 0.6 to 0.8 ms more in Chrome, 0.7 to 1.1 ms in Safari and up to 0.4 ms in Firefox; in Chrome and Safari the text after that is already level or faster. The first `prepare()` of interface labels is slower by 10% or more in some languages, most of them with long words: in Firefox by 17% to 36% in seven of the 36 languages timed, among them German (17%), Finnish (21%), Tamil (22%), Telugu (24%) and Armenian (36%), and in Chrome by 11% to 29% in three, Telugu, Armenian and Tamil. English labels take 20% to 41% less time in the three browsers, and no language is slower in Safari. Most of that cost is the widths a word 80px or wider now gets for each of its letters when it is first prepared, for a line narrower than the word, which cuts it between letters.
- In `pre-wrap` text, tab stops now follow each browser. Chrome and Firefox count letter spacing in every stop, so a run of tabs under negative `letterSpacing` no longer collapses to one stop's width. A tab closer to its stop than the browser's minimum, half a space in Chrome and Safari and half a `0` in Firefox, takes the stop after it. In Firefox, which doesn't hang tabs, a word whose tab doesn't fit moves to the next line with the tab, so tab-separated text such as a pasted table or indented code wraps where Firefox wraps it (#240, #395).
- A rich-inline atomic item's (`break: 'never'`) own leading or trailing white space no longer gives a gap before or after it, as browsers trim that white space inside the item's box: where only that white space stood, `gapBefore` is now 0, and `gapItemIndex` -1, where 0.0.9 measured a space in the atomic item's font. An atomic item of only white space is an empty box as wide as its `extraWidth`, as browsers lay out an inline-block that holds only white space, where 0.0.9 made it a collapsed space with no `extraWidth` (#369, #460).
- Pretext now finds grapheme clusters with the character rules each browser ships instead of `Intl.Segmenter`, which it needs only for text in Thai, Lao, Khmer, Myanmar and the other Southeast Asian scripts written without spaces (#344).
- Chrome, Safari and Firefox now find where lines can break with ports of each browser's own line breaker and its data, in place of Pretext's own rules, so lines break where the browser breaks them in many more cases, such as around CJK punctuation and quotes, dashes, URLs and Thai (#340). Among the breaks that moved (#228, #232, #233, #234, #243, #245, #249, #250, #270, #276, #288, #289, #290, #291, #309):
  - Lines can break after `؟`, `؛` or `۔` before a following word, after a `?` that follows a space or a zero-width space, and after `!` or `?` before a symbol such as `©`, `¿` or `€`. In Chrome and Safari they can also break after `?` before `$`, `%`, `+`, `|` or `-`, while `!` still stays with those and with a following ASCII letter or digit; in Firefox they can break after `!` before a letter or digit, and `!` and `?` stay with a following `-` or `|`.
  - In Chrome and Safari, a hyphen or dash at the start of a word, such as U+2010 HYPHEN, U+2012 FIGURE DASH or U+2013 EN DASH, stays with the letter after it; `-` does so only before a letter outside Latin-1. In Firefox, a hyphen stays with a number after it, as in `2025-08-01` or `log-2026`, and a line can break after `/` before a letter, as in `and/or` or `example.com/docs`, though not before a number, as in `1/2`.
  - A figure space (U+2007) keeps the text on both sides of it on one line, like a no-break space, and a zero-width joiner keeps the character after it.
  - Lines no longer start with closing punctuation or other marks that can't start a line, such as `。`, `，`, `」`, `､`, `］` or `゛`: such a mark stays with the text before it, CJK or not, as in `xxxx，` or `😀。`, and after CJK text so do `'`, `/`, `|`, `‼` and `％`. A word that doesn't fit a line with its mark breaks before the mark.
  - After CJK text, `.`, `,`, `:`, `;`, `)`, `]`, `%` or `"` keeps a following word or number on its line, and `!`, `}`, `/` or `|` keeps what each browser keeps: Chrome ASCII letters and digits; Safari digits, and letters only after a `}` that follows an ideograph or Hangul syllable; Firefox only digits after `/`. A time or number before closing punctuation such as a full-width comma, as in `00:00:00，`, stays whole.
  - In Chrome, lines can break between a fullwidth closing bracket such as `」` or `）` and a following ideograph, kana or Hangul syllable.
  - Small kana and `ー` after CJK text can start a line in Chrome, in Safari only on pages whose `<html lang>` is Japanese or Korean, and not in Firefox; where they can't, they also stay with a letter or digit before them, as in `約3ヶ月`.
  - With `word-break: keep-all`, lines in Chrome and Firefox no longer break after `ー` in words such as `ラーメン`, nor in Chrome after an iteration mark such as `々`. In Chrome and Firefox they can break before an opening bracket after CJK text, as in `서울(한국)에서`, before `「` or `（` after Latin letters or digits, and next to Thai text; in Chrome also next to emoji and symbols such as `★`, and before an opening quotation mark or after a closing one between CJK characters, as in `他说“你好”然后`; in Firefox also after a flag emoji.
  - Text that stays together on a line, such as `漢。` or `「漢`, breaks between characters when it doesn't fit a line, instead of overflowing, and a run of opening brackets stays with the word after it, as in `「「tail`.
- Rich inline now lays its items out as one paragraph, as a browser lays out a paragraph's spans: it finds where lines can break in the items' joined text once and measures each item in its own font, so its lines break where the same text in one element does. Each item continues the line before it, and a line ends between items, or inside one, only where the joined text has a break opportunity, in every browser, in engines Pretext doesn't recognize and in runtimes such as Node, Bun or jsdom. 0.0.9 prepared every item apart and laid each out as if it started a line, so a line could end at any item boundary, or between the letters of an item's first word to fill the line (#241, #287, #301, #327, #359, #369, #372, #373, #460):
  - Punctuation such as `,` or `)` at the start of an item stays with the word before it, and a word split across items wraps as one word, moving to the next line whole where it doesn't fit. Items without a space between them still break where the joined text allows it, such as between CJK characters, at Thai word boundaries or after `-`. In Chrome and Firefox, where items split a word, as when part of a Thai or Myanmar word is styled, lines end at that word's own breaks. In Safari, breaks inside each item still come from that item's own text, as Safari wraps each span, so a Thai, Lao, Khmer or Myanmar word split across items wraps like Safari's spans.
  - A soft hyphen that starts an item after other text, or ends an item, is a break there, and a line that ends at it ends with a hyphen, which its width counts and its fragment's text shows; 0.0.9 painted and counted none there. In Firefox that holds before a combining mark too; after an ideograph or emoji such a break needs no room for a hyphen, as Firefox draws none there; two soft hyphens that start an item break as in one element; and so does one right after a space, with no hyphen.
  - An item holding only a soft hyphen is such a break too, and keeps the collapsed space before it, which its fragment names in `gapItemIndex`; an item that starts with a soft hyphen and a space keeps that space after other text on the line. White space between the soft hyphens of such an item takes room after other text in Chrome and Safari, as in one element, and a line too narrow for anything ends at its first soft hyphen. An item of only soft hyphens or a zero-width space gets no fragment on a line whose start consumes it, where 0.0.9 gave it one that took no room.
  - In Firefox, white space collapses across soft hyphens and bidi controls, invisible direction characters such as U+202A, from one item into the next, as Firefox collapses one run of them whichever element holds it, so an item holding only white space and bidi controls such as LRM between words takes the room of one space, not two, and a soft hyphen or bidi control that starts an item ends that run. In Chrome, a newline next to a zero-width space in the item before or after it goes, as in one element, instead of leaving a space.
  - Cursors changed meaning, which breaks code that read them as places in an item's own text. A line's `end` and a fragment's `start` and `end` now count segments of the item's part of the paragraph, and are only for passing back to `layoutNextRichInlineLineRange()` and `materializeRichInlineLineRange()`. On 0.0.9 they indexed the item's own prepared text, `prepareWithSegments(item.text)`, and they no longer do: they differ, among others, for an item that starts with white space after another item's text, whose first segment is now that space; for an atomic item, which is one segment; for an item that starts inside a word whose breaks depend on the whole word, as a Thai word's do in Chrome and Firefox; and for an item with `extraWidth` that starts with a zero-width space, whose start is now a segment of its own before that space. A paragraph of one text item that isn't atomic and has no `extraWidth` keeps that text's own cursors. To find a fragment's text in its item, read the materialized fragment's `sourceStart` and `sourceEnd` (under Added).
  - Four things got worse. A zero-width space in an item of its own, such as the placeholder an editor keeps in an empty styled run, no longer gets the line of its own that the browser gives it: after a space that ends its line, where the paragraph comes out a line shorter than the browser's for the few pixels of width where that line's text fits and the space doesn't; and after content wider than its line, such as text laid out at a width narrower than a letter or, in Chrome and Safari, an atomic item that doesn't fit. In Chrome and Safari, an item with `extraWidth` that holds only a zero-width space, such as an empty code span kept open with one, stays on a line where only half its `extraWidth`, the end padding, doesn't fit, so that line's `width` is more than `maxWidth`; 0.0.9 moved it to the next line, which is where those browsers put it after a space. In Firefox, a line that ends at a space before a soft hyphen in another item reports that space in its width, one space wider than Firefox paints. Also in Firefox, where an item ends with a space and the next starts with a bidi control, such as U+200E, and another space, a one-word line that ends at the first space reports that space in its width as well, and a longer line that fits only without that space now gives up its last word to the next line, which Firefox does in some such paragraphs and not in others, so the paragraph can come out a line taller than Firefox's.
- The values in a `prepareWithSegments()` handle's `kinds` changed. `'glue'` is gone: a segment of no-break spaces or a word joiner is now `'text'`, so code that compares a kind with `'glue'` no longer type-checks. Two are new: `'zero-width-glue'`, a zero-width space or soft hyphen the browser doesn't break after, as before a combining mark, and `'control'`, in Safari a next-line character (U+0085) (#240, #340).
- The type of a `prepareWithSegments()` handle now shows three read-only fields and nothing else: `segments`, `kinds` and `widths`, each segment's width in px. The eleven others that 0.0.9's type showed are the library's own working data for laying out lines, which changes with engine fixes: six are gone (under Removed), and reading any of the rest no longer type-checks. For a text's width, call `measureNaturalWidth()`; for a line's, read the line's `width`. Each letter's width (`breakableFitAdvances`) and the hyphen's (`discretionaryHyphenWidth`) have no public equivalent. All three are read-only: to pass one on as a `string[]` or `number[]`, or to write to it, copy it first, with `prepared.segments.slice()` or `Array.from(prepared.widths)`. `widths` is typed `ArrayLike<number>`, with an index and a `length`, so `for...of`, spread and `reduce()` on it need that copy too (#450).
- A JSON copy of a prepared handle, `JSON.parse(JSON.stringify(prepared))`, no longer lays out, where 0.0.9 laid it out: most line functions hang on one without returning, on a copy of a rich-inline handle too, and `layoutNextLine()` can return a line without its hyphen, or empty lines without end. `structuredClone()` and `postMessage()` copies work, and cursors and line ranges are still plain JSON. A handle works only with the version of Pretext that made it: one made by 0.0.9, as kept in IndexedDB or sent by a worker on an older bundle, throws a `TypeError` in this version's line functions, so prepare the text again. A handle also holds a typed array now, so a deep freeze of one throws; freezing the handle itself still works (#340, #460).
- Safari's line breaking follows Safari 27. Safari 26, on macOS 26 and iOS 26, breaks differently around curly quotes and guillemets, after punctuation with `word-break: keep-all`, at U+2028 and U+2029, and after a first character too wide for its line (#340).
- In Chrome, text on a page without a `lang` now breaks and measures under Chrome's UI language, as Chrome lays it out: under a Chinese UI, curly double quotes follow the line-break rules of CJK brackets, so a line doesn't end with “ or start with ” (#340).
- `setLocale(locale)` now sets the language that later `prepare()`, `prepareWithSegments()` and `prepareRichInline()` calls break lines and measure under, in place of the page's `<html lang>`, which a worker doesn't have; `setLocale()` without a locale goes back to `<html lang>`, and `setLocale('')` is a page without a language, where 0.0.9 took an empty string as no argument. It no longer passes the locale to `Intl.Segmenter`, whose word boundaries Pretext now reads only inside Thai, Lao, Khmer and Myanmar text, where no locale changes them (#340, #356).
- `prepare()`, `prepareWithSegments()` and `prepareRichInline()` now throw a `RangeError` for a `letterSpacing` that isn't finite, such as `NaN` or `Infinity`, which gave lines of width `NaN`, or a line per grapheme (#356).

### Removed

- `prepareWithSegments()` no longer returns `segLevels`. Those approximate bidi levels per segment couldn't produce visual order, and computing them slowed every `prepareWithSegments()` and rich-inline preparation, most for Arabic and Hebrew text. To draw mixed bidi text, render each paragraph as one DOM element with its direction set, and the browser orders every line. Lines drawn separately, such as with Canvas `fillText()`, are each ordered as their own paragraph, so numbers or punctuation next to a line break can come out in a different order (#258).
- A `prepareWithSegments()` handle no longer has `lineEndFitAdvances`, `lineEndPaintAdvances`, `breakablePreferredBreaks`, `spacingGraphemeCounts` or `chunks`, fields README never documented but 0.0.9's published type showed; none has a public equivalent (#255, #340).
- The npm package no longer includes the demos (`pages/demos` and `pages/assets`). They live in the repository (#342).

### Fixed

- A word too long for its line, such as a URL, a message placeholder or a long compound, is now cut where Chrome cuts it when its letters kern, and closer to where Firefox cuts it, in a word 80px or wider. Both browsers fit the letters as the word shapes them, where 0.0.9 added up each letter's own width and so moved a letter to the next line too early, or, where the rest of the word then looked too wide, gave the paragraph a line too many. In Firefox, Pretext still doesn't count the kerning between the last letter of a line and the first of the next where the browser counts it, so where those two letters kern, as in a long run of `AV`, the cut can still fall a letter from Firefox's and the word take a line more or fewer. Firefox also keeps the letters of a ligature, such as `fi` in fonts that join it or Armenian `ու`, on one line, and moves them to the next together where they don't fit; Pretext can still cut between them in a word of more than 96 letters. The widths for this are measured when such a word is first prepared, the cost new labels in languages with long words pay (under Changed) (#340, #435).
- In Chrome, where a column is too narrow for the start of an ID, a date or a phone number and the line is cut right before a hyphen with a digit after it, the hyphen now stays with those digits, which wrap where the line is full, as Chrome lays them out: `TKT-84565` in 16px Helvetica Neue in a table cell 31px wide is `TKT` / `-84` / `565`. The hyphen used to take a line of its own there, so such a cell came out a line taller than Chrome's (#NNN).
- In Firefox, a rich-inline `break: 'never'` item that takes no room, or a box of width 0, that falls past the end of a full line, as after a space that doesn't fit, now lands on the line Firefox puts it on. It stays at the end of the full line where it is the paragraph's last item, where a box or chip with a width follows it, or text without `extraWidth` that starts with a space, and in `pre-wrap` after spaces that hang. It starts the next line where text or an item with `extraWidth` follows it directly, or where the white space before it follows text already wider than the line. It used to start the next line in every case, which could give the paragraph a line more than Firefox lays out and put the item's fragment, and the height an app gives each line from its boxes, on the wrong line (#387, #405).
- In Chrome, lines no longer come out wider than Chrome lays them out in fonts that kern letters against the space, such as Arial, Helvetica, Times New Roman, Trebuchet MS, Roboto, Avenir Next and Gill Sans. Chrome tightens a space before a capital such as `A`, `T` or `Y`, and in some fonts the space after many words, which Chrome's Canvas doesn't report for words measured apart, so a line with several such words was up to a few pixels too wide: a paragraph of card-length text took a line more than Chrome gave it at about one width in 600 in Arial, and one in 75 in Gill Sans, and a bubble sized to its widest line was that much too wide. Pretext now reads that kerning from Canvas: the first text with a space in a font costs two more `measureText` calls, which tell whether the font kerns the space, and only a font that does costs more, up to three calls for each distinct first or last character of its words other than ideographs, kana and Hangul syllables, so the first paragraphs in such a font make the most extra calls and later ones next to none. Where a line ends at a word that kerns with the space after it, the word is measured without that kerning, as Chrome lays it out in centered, right-aligned, justified or underlined text and in text directly inside an element with a background; in plain start-aligned text Chrome keeps the kerning there, so such a line can still wrap one word sooner than Chrome, as before, and never later. A font that kerns only characters outside ASCII against the space, as Tamil MN and Malayalam MN do, and text that holds right-to-left letters or bidi controls, measure as before. In rich inline, a collapsed space at an item's start or end is measured with that item's text beside it, so `gapBefore` and the line's width hold this kerning too: `A` and a space in 16px Arial are 0.88px narrower (#408, #423, #426, #460).
- In Firefox, a lone carriage return or a form feed in the default `whiteSpace: 'normal'` now takes no room, as Firefox draws it, inside a rich-inline item and at its start or end too: `ab\rcd` is as wide as `abcd`, and a line can still end after `ab`. Before, it took the room of a space. `\r\n` is still one space. White space that starts the next rich-inline item after one is measured in that item's own font and letter spacing, as Firefox draws it, where the item that held the carriage return or form feed measured it (#399, #460).
- In Safari, a lone carriage return in the default `whiteSpace: 'normal'` now takes no room, as Safari draws it, inside a rich-inline item and at its start or end too: `ab\rcd` is as wide as `abcd`, and no line ends at the carriage return in text that is all Latin-1; where the text holds characters outside it, such as Cyrillic, Arabic or Chinese letters, a line can end after the carriage return where Safari ends one, as in `бв\rcd` and not in `бв\r12`. On 0.0.9 it took the room of a space and a line could end at it, so a line holding one measured a space too wide and a paragraph could come out a line taller than Safari's. `\r\n` is still one space, and white space that starts the next rich-inline item after a carriage return is measured in that item's own font and letter spacing. One kind of font goes the other way: where the first installed family of a font list is `monospace` or one of macOS's own fixed-pitch fonts, Menlo, Monaco, Courier, Andale Mono or PT Mono, Safari gives the carriage return a character's width. For one carriage return between two letters the space 0.0.9 gave it was as wide; now a line holding one measures a character too narrow in those fonts, and a paragraph can come out a line shorter than Safari's. Courier New, `ui-monospace` and web fonts aren't among them (#455, #460).
- In Firefox, spaces on both sides of a soft hyphen, as in `ab`, space, soft hyphen, space, `cd`, now take the room of one space, as Firefox collapses them into one, instead of two (#399).
- In Chrome and Firefox on macOS, at small font sizes, an emoji character that a text font draws no longer measures 4-5px narrower than the browser draws it, which had the browser wrapping a line that Pretext said would fit: one the named font has a glyph of its own for, such as `⚡` in Menlo, `⬜` in Inter or `⚪` in Hiragino Sans, or one before the text-presentation selector U+FE0E. A pictograph written with no U+FE0F after it that the system's emoji font draws all the same, such as U+1F336 `🌶` or U+1F5D1 `🗑` in Arial, and an emoji sequence that the emoji font has no glyph for, and draws as two emoji, no longer measure 4-5px wider than drawn (#398).
- In Chrome and Firefox, `letterSpacing` no longer adds space after the letters of Arabic, Persian, Urdu and the other joined scripts (Syriac, N'Ko, Mandaic, Mongolian, Phags-pa, Hanifi Rohingya), as the browsers add none: Chrome, which also leaves out the digits, brackets and punctuation inside such text and spaces only its spaces, and Firefox, which keeps spacing those. Such text measured too wide by the spacing times its letters, or too narrow under negative spacing, so its lines broke elsewhere than the browser's. Safari spaces every letter, and so does Pretext there, as before. This is Chrome's rule since 149. Chrome 138 to 148 leave those spaces unspaced too, and Chromium before 138 spaces every letter, as Pretext did; on those, as in an older Electron app or WebView, Pretext's width for such text is now off by the spacing times its spaces, or times its letters (#397).
- In Firefox, `letterSpacing` now counts as Firefox lays it out, in whole steps of 1/60px: at -0.08px each character takes -5/60px, and a spacing under 1/120px none. A spacing between steps, such as -0.08px or one computed from an em value, made each line a little wider or narrower than Firefox's, 0.1px over 30 characters at -0.08px, so a word could land on another line (#397).
- In Chrome and Firefox, text with `letterSpacing` in a font with `fi`, `fl` or `ffi` ligatures, such as Roboto, Futura, Hoefler Text or Iowan Old Style, now measures as wide as the browser draws it. Browsers turn those ligatures off under any letter spacing, and Pretext measured the words with them, up to 1.3px too narrow per word at 16px, so a line could hold a word the browser wraps and an element sized to the widest line could wrap again. Safari's Canvas can't measure such text without its ligatures, so there the widths stay that much too narrow (#397).
- Where the hyphen of a chosen soft hyphen doesn't fit, the line now ends at the latest earlier break that fits, such as a space, a zero-width space, an earlier soft hyphen, the `-` of a compound such as `contre-pro\u00ADposition`, a dash, or a break between Chinese or Japanese characters, as the browsers lay it out, instead of keeping the hyphen past the line's end; so does a line whose word holds a control character. Text with many soft hyphens, such as hyphenated German, often took other breaks than the browser's, sometimes with a line fewer. With `letterSpacing`, Chrome's visible hyphen no longer gets letter spacing of its own (#239, #340, #396, #446).
- A line that ends at a soft hyphen is now fit and measured with the hyphen the browser draws there, U+2010 HYPHEN where the font has one, in place of `-`. Some fonts draw the two differently, such as Inter, whose U+2010 is 1.6px narrower at 16px, and Chinese fonts such as Songti SC, whose U+2010 is a full em wide, so such lines now break where the browser breaks them and report the width it paints. The line's `text` still ends with `-` (#396).
- In Safari, a line separator or paragraph separator (U+2028 or U+2029) now ends its line, as Safari lays it out, in normal white space as in `pre-wrap` and inside a rich-inline item, where 0.0.9 kept the text after it on the same line. A line holding only soft hyphens or spaces between two separators counts as a line (#340, #349, #369, #381).
- Under negative letter spacing, a rich-inline line that starts inside an item no longer starts its first fragment's text with a space. Where the last word of the line before just fit, as happens at the letter spacing apps give body text, such as −0.08px, the next line's first fragment started at the space after that word: text such as ` cd`, which Canvas `fillText()` or `white-space: pre` painted one space to the right. It now starts after the space, as the browsers start that line and as `layoutWithLines()` does. At any letter spacing, a rich line's first fragment now starts after the spaces and soft hyphens a line start skips, where its `start` cursor used to sit before them (#380).
- In Firefox, lines break around bidi controls, invisible direction characters such as LRM, RLM and LRI, as Firefox breaks them, as if they weren't there: a control no longer takes a line of its own at a narrow width or separates an accent after it from the letter before it, a line that wraps after a space and a control no longer counts the space in its width, the spaces on both sides of a control take the room of one, and a control inside a word no longer takes letter spacing (#368).
- Browsers whose layout engine Pretext doesn't recognize, such as Samsung TV web views, now follow Chrome's rules throughout. Before, a soft hyphen's hyphen also took letter spacing of its own there, a line whose hyphen didn't fit kept it overflowing instead of ending at an earlier break with room for it, and on desktop systems a line starting inside a word that holds an invisible character, such as a word joiner, didn't measure the rest of the word on its own as Chrome does (#356).
- `materializeLineRange()` and `materializeRichInlineLineRange()`, given a range that ends past its text, such as one kept from a longer text that was since prepared again, now build the text up to its end. Before, each missing segment added `undefined` to the line's text, and a range ending at segment `Infinity` ran until memory ran out (#353).
- In `white-space: pre-wrap`, a line holding only soft hyphens before a newline, at the start of the text or after another newline, now counts as a line, as browsers draw it, instead of disappearing (#349).
- In Safari, on pages with a language, text in `serif`, `sans-serif`, `cursive`, `fantasy` or `monospace`, or falling back to one of them, now measures in the font Safari draws it with there, such as Apple SD Gothic Neo for `sans-serif` on a `ko` page and Menlo for `monospace` on an `en` page, instead of the font those names give a page without a language (#340).
- In Chrome, CJK punctuation next to other punctuation or at a line end now takes the narrower width Chrome's `text-spacing-trim` gives it, also where a rich-inline item boundary splits the pair, such as `」` ending a bold item before `。`, whatever the two items' fonts; a closing mark such as `」` or `）` takes it before a newline in `pre-wrap` or before a space too, where nothing earlier on the line can wrap, as at a narrow width (#340, #366, #425, #460).
- In Chrome and Firefox, ideographic spaces (U+3000) at a line end now hang past it, as spaces do, instead of wrapping to the next line (#340).
- A run of no-break spaces (U+00A0, U+202F or U+2007) between other break opportunities, such as between two spaces, now breaks where it overflows its line, as browsers do, instead of staying on one line (#340).
- In Firefox, a newline between East Asian characters no longer adds a space, and on `ja` and `zh` pages neither does one next to East Asian punctuation (#340).
- In Firefox, a soft hyphen where the line could break anyway, as after a space or between an ideograph and a Latin letter, no longer draws a hyphen or needs room for one (#340).
- In desktop Chrome and Firefox, where a word holding an invisible control, such as a word joiner, breaks across lines, the part that starts the next line is now measured as each browser shapes it at a line's start, so narrow text around such controls wraps more as those browsers wrap it ([a28b5428](https://github.com/chenglou/pretext/commit/a28b5428)).
- Paragraphs made only of zero-width spaces now occupy one line instead of disappearing (#223).
- A zero-width space at the start of a paragraph or after a hard line break no longer disappears when the following text wraps to the next line (#227).
- In Chrome, text prepared after changing `<html lang>` now uses the fonts for the new language, even when the font string is unchanged (#230).
- In Safari, a word followed by a space now keeps its kerning with that space, so letters such as `A` in Arial or Times New Roman fit narrow lines as they do natively (#236, #271).
- Reported line widths are now clamped at 0 instead of going negative, for example with strongly negative `letterSpacing` (#236).
- Chrome, Firefox, Edge and other browsers on iPhone and iPad, and in-app web views on iPhone, iPad and Mac, now wrap text as Safari does, since they use WebKit. Previously, some of them got rules meant for other browsers, such as breaks after punctuation with `word-break: keep-all`. In Safari, text prepared in a web worker now gets the same rules as on the page (#237).
- In Chrome and Firefox, a newline next to a zero-width space no longer adds a space in `white-space: normal`, matching the browser (#238).
- In Safari, a next-line character (U+0085) now stays on the same line as the text before it, and lines can still break after it. `letterSpacing` no longer adds space after U+0085, except next to text that Safari shapes as complex text, such as Arabic, Devanagari or a combining mark (#240).
- When a line's first word is wider than the line, a following space or zero-width space now ends that line in `layoutWithLines()`, `walkLineRanges()`, `layoutNextLine()`, `layoutNextLineRange()` and rich-inline layout. Previously, other content such as a soft hyphen or a word joiner, or `letterSpacing`, moved it to the start of the next line. Plain-text line counts and widths don't change (#272).
- A negative `maxWidth` now lays out as 0 does in `layout()` and the other plain-text line functions. It could give another line count than 0 under strongly negative `letterSpacing`, or for text holding a word joiner. `measureRichInlineStats()`, `walkRichInlineLineRanges()` and `layoutNextRichInlineLineRange()` now lay a negative `maxWidth` out as 0 too, and one under 1px at that width, as the plain-text functions do and as browsers lay out an element that narrow. Before, they laid every such width out as 1px. At a width of 0, as of a container not laid out yet, ordinary text takes the lines it takes at 1px, about a character a line. What changes is content narrower than 1px, such as letters under a `letterSpacing` about as negative as they are wide, which shared a line and now take a line each (#272, #462).
- With `word-break: keep-all` in Chrome and Firefox, a URL containing a second `www.` or scheme such as `https://` before its query, as in `x中www.a/www.b?q`, no longer loses text (#269).
- Rich-inline layout now keeps text, or a `break: 'never'` item, on a line when it overflows by no more than 0.005px, or 1/64px in Safari, as it already did inside one item. Previously, at some widths, layout took one more line than at a slightly narrower width (#281).
- In `pre-wrap`, a line that wraps no longer counts the spaces it ends on in its width, and spaces before a newline or at the end of the text count only as far as they fit, so elements sized from `measureLineStats()` or `walkLineRanges()` no longer run past the text. In Chrome and Safari the same holds for tabs, and a run of spaces and tabs at the end of a line now stays on that line whole, instead of starting the next line with a tab or a space after a tab. Firefox doesn't hang tabs, so there a tab still counts in the width (#308).
- In Chrome and Firefox on macOS, U+FE0F after a character that isn't emoji, such as a letter, a space or U+3000, no longer makes text measure narrower than the browser draws it at small font sizes (#320).
