# Preparation ownership account

Read-only account of the live redo worktree at committed `198193903861127670cd3f246f2cb1d8b65c12aa`, with round 3 runtime changes only in Blink `line-breaker.ts` and Gecko `lines.ts`, versus actual main `2e5e2bdaee398784b9cf27b24ca96df2e85396b8`. Consulted `~/github/vibescript/docs/engineering.md`. No implementation, tests, browser jobs, timings, or large captured-source parsing. This is a consumer/lifetime account, not a ranking of measured costs.

## Blink's current ownership chain

Let M be the original source's UTF-16 length and N the post-whitespace content's UTF-16 length. N can include generated units that have no source offset. Even plaintext goes through the inline-tree index and content builder.

1. `indexContent(paragraph)` walks the input with an explicit stack. It retains each original leaf string, its source start/parent/event, the original element references, and open/close/text/atomic/br/wbr events. It also assembles `index.text` with `text += node.text`. The original paragraph is retained separately in `BlinkPrepared.paragraph`.
2. `buildContent` walks those events, derives styles and text-layout eligibility, and calls `Builder.appendText(leaf.text, leaf.start, run, style)`. `Builder.units: number[]` holds emitted UTF-16 units; `Builder.src: number[]` holds corresponding original offsets, or -1 for generated/element units. Both are temporary preparation storage.
3. The builder can temporarily erase and then restore a trailing collapsible space. `removedAt` keeps the physical unit until the item is finalized; `unitAt` and item offsets account for it. `finalizeSpace` splices both arrays and adjusts subsequent opaque-item offsets. This is real mutable construction state, not merely an append-only string concatenation.
4. `finish()` finalizes that space, constructs `content.text` with 4096-unit `slice`/`String.fromCharCode` chunks, and copies `src` into `Int32Array sourceOffsets`. The builder's number arrays then become unreachable; `items` is handed onward. Thus construction overlaps temporary unit/offset arrays with the final string and typed offset array. JavaScript engine flattening and physical string sharing are not established by these source operations.
5. Blink prepare allocates `contentOffsets: Int32Array(M).fill(-1)` and traverses `sourceOffsets` while constructing `sourceRuns`. Kept source units receive their content index; removed source units remain -1. `sourceRuns` stores maximal negative-source runs as numeric start/end pairs, allowing logarithmic jumps over generated stretches rather than scans repeated at every line boundary.
6. The prepared paragraph retains the original index, transformed text, both maps, source runs, items, styles, shaping groups, Canvas pool, and other structural facts. These share the paragraph's lifetime; there is no per-text global answer cache in redo. Inspected preparations retain additional source/grapheme run indexes and diagnostics. Plain preparations omit those inspection records, but still permit `linePieces()` later.

The two dense maps have an exact typed-array payload of 4N + 4M bytes, before headers. This is not the heap size of preparation: it excludes temporary number arrays, strings, groups, styles, contexts and other arrays. Nor is the aggregate source text necessarily an additional physical copy for a single leaf: JavaScript strings may be shared or represented as ropes. A logical representation count cannot determine physical storage cost.

## What currently consumes each representation

| Representation | Current consumers | What the access establishes |
| --- | --- | --- |
| Original paragraph and leaf strings | Style derivation, event construction, `runOfSource`, fragment run/event identity; original elements also supply atomic and box facts | Original input identity and boundaries remain relevant even when its whitespace is removed. This does not require an additional concatenated source string. |
| `index.text` | In Blink's engine, every production reference found uses `.length`: map allocation, end-of-source line cuts and gap bounds. The shared painter independently calls `indexContent(paragraph)` and reads its own aggregate source characters/slices. Gecko prepare also uses the shared aggregate as actual text. | Blink's prepared index currently needs source length, not aggregate source character access. Removing that aggregate from Blink alone is an unexamined exact alternative. The shared index cannot simply lose it while those other consumers still read it. The painter does not reuse the prepared index. |
| `p.text` | Line breaking and shaping use random UTF-16/point reads and slices. Grapheme/continuation/ligature/font/group facts are indexed against it. `fragmentsOf` reconstructs painted strings from its characters. | Current code expects a stable transformed coordinate space and an actual string for Canvas/Unicode operations. It does not prove that an unchanged input must be reconstructed from numeric units first, or that every intermediate needs to own a string. |
| `sourceOffsets[N]` | `lineSourceRange` maps the next content cut to source; gap ranges map first/last kept units; hyphen fragments compare against the source end; inspection identifies generated units | Source cuts are part of full and range API output, so this need survives range-only use. An identity mapping or monotone spans could answer the same questions; the dense array is the current implementation. |
| `contentOffsets[M]` | Plain `fragmentsOf` loops source units, classifies kept/removed units, and reads their transformed characters. Inspected `mappingOf` emits kept/collapsed/generated mapping records and finds collapsed positions. | The inverse map serves plain painted pieces as well as inspection. It is not read by the source-range calculation itself. Eager construction before any piece request is not proven necessary, but changing it requires preserving later `linePieces` behavior on an ordinarily prepared handle. |
| `sourceRuns` | Plain and inspected boundary/range readers jump over generated stretches | Its purpose is bounded repeated lookup. A replacement must preserve that property for arbitrarily long generated runs; deleting it and scanning is a potential regression. |
| `canvasText` | For eligible plain 8-bit/unsegmented/no-SHY text, shaping selects equal-length narrow or space-widened spellings | These are explicit Canvas spellings, not replacements for source or painted text. Their storage/partition behavior is part of current measurement rules. No borrowing/cache change should silently alter those rules. |
| Groups and structural arrays | `groupOfUnit`, grapheme starts, continuations, ligature/font facts, clusters and segment facts guide break/shaping decisions; groups retain lazy prefix/pair/wide measurements by offset | These facts survive widths and have actual consumers. For each group's length L, the three Float64Arrays retain 24L bytes before headers even when entries are initially NaN. Their eagerness/density is a separate architecture question, not a demonstrated requirement. |

## Main's preparation uses a different lifetime and output contract

Actual main `analyzeText` temporarily retains `{source, normalized, texts, starts, kinds, isWordLike}`. Normalization can reuse the input string if unchanged; segmentation builds its own strings/arrays and performs merge passes. `measureAnalysis` consumes this analysis and creates per-handle widths, break kinds, overflow fit advances/preferred breaks, hard-break chunks and conditional spacing/entry/hyphen facts. Main's ordinary `prepare()` does not retain source text, normalized text, starts, segment text or source-to-content maps in the returned handle. `prepareWithSegments()` additionally retains segment strings. Neither handle provides redo's original UTF-16 source cuts, richer inline items, or the same inspected geometry.

This smaller returned handle does not mean all text-derived allocations die after main preparation. Main's module-level `Map<font, Map<segment, SegmentMetrics>>` retains measured strings and metrics across texts. Metrics may own grapheme advances and entry geometry; prepared handles often retain references to these same arrays. A following-space variant has another per-font string cache. `clearCache`, locale changes, and page-language changes clear shared answer caches; a language change also recreates the measurement context. Already returned prepared handles retain their referenced fit data. The shared caches have no source-level size cap in these files, so reuse and retained growth both matter.

Redo's group-offset answers live with one prepared paragraph instead. Public prepare supplies a fresh pool by default; Blink/WebKit callers may deliberately keep a pool to reuse settings-specific Canvas contexts, but font-fact answers are local to each preparation and are asked again. Gecko deliberately owns a fresh pool. The pool's between-preparation cap is 512 settings, not a bound on declarations inside one paragraph. These are different policies and lifetimes; a main comparison includes them.

Do not transfer main's measured-string Map to redo as a routine optimization. Redo's `measure/canvas.ts` records the relevant source/probe evidence that keyed string use can change V8 string storage and therefore Blink Canvas shaping. Existing redo offset caches avoid keyed use of measured strings. Any new reuse policy must preserve actual settings, questions and string handling first. This account makes no claim about fonts that Canvas cannot reveal.

For context, the preserved round2 Latin-120 trace has 16,057 redo prepare Canvas questions versus 1,476 in main, with unchanged queries across redo variants. This is an observed policy/work difference, not proof that 16,057 questions are necessary. The bounded same-function preparation controls also did not establish a repeatable nullable-metadata slowdown or a GC/JIT/native cause. Source ownership should be investigated independently of those causal guesses.

## Smallest next prototypes

The smallest isolated change is to have the builder carry **the actual emitted text's 8-bit status**, alongside its existing source-storage flag, and remove prepare's separate `is8Bit` string scan. All units already pass `push`; the only later unit deletion here is a collapsible U+0020. The existing `hasNonOrc16Bit` is not interchangeable: it intentionally observes original leaf storage and treats literal U+FFFC differently from an atomic-generated U+FFFC. This would remove a pass with no guessed Unicode shortcut or extra per-unit array. It may provide too little gain, or the per-push branch may cost more; it needs the existing exact proofs and a bounded cost check before retention.

The smallest prototype that addresses retained representation is to replace **only source-map identity cases** with an exact implicit identity result, retaining the dense transformed fallback. A builder can establish identity while it emits/finalizes source offsets: N equals M and every final emitted unit maps to its own source offset, with no generated or removed units. Both direction lookups then return the requested index without allocating the two dense arrays; `sourceRuns` has no negative runs. Keep transformed/inspected/piece behavior exact, and expose this through one internal source-map representation rather than adding an identity flag while leaving both arrays allocated. This is unexamined, not a proposed acceptance waiver. Benchmark its extra lookup dispatch as well as its construction and retained payload; mixed/generated/collapsed worst cases must stay bounded.

A broader next step is to emit kept/generated spans and derive forward/inverse lookups or iterate spans directly in `fragmentsOf`. That could remove temporary offset duplication and permit original-string borrowing, but it changes many consumers and must account for trailing-space restoration, empty leaves, styled boundaries, hard breaks, literal versus generated ORC, malformed UTF-16 and Canvas storage semantics. Do not add a span tree beside unchanged old arrays and call that simplification. No such alternative has been proved by this account.

The aggregate source string used only for length is another exact cleanup candidate, but it is probably low value for the current one-leaf plaintext batches, where concatenation may already share the original string. It should follow evidence about multi-leaf inputs, rather than be sold as an established preparation bottleneck.
